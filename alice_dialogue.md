## Цель семинара

Цель семинара BigDatapedia Workshop — дать участникам **практико-ориентированные навыки построения реального потокового пайплайна обработки больших данных** на стеке Spark Streaming + Kafka + Hadoop + PostgreSQL.

Ключевые задачи, которые решаются в рамках семинара:

- **Освоить сквозной поток данных**: от генерации и отправки в Kafka до чтения Spark, агрегации, записи в БД и визуализации в Grafana.
- **Научиться разворачивать и настраивать многоузловой кластер** в Docker: распределение ресурсов (память, ядра), настройка исполнителей и драйвера, уменьшение числа разделов для производительности.
- **Понять архитектуру потоковой обработки**: микропакетный режим Spark Streaming, контрольные точки (checkpoints) для отказоустойчивости, окна агрегации, синхронизация с источниками.
- **Получить навыки, релевантные собеседованиям**: работа с executor’ами, мониторинг, тонкая настройка параметров кластера, обработка ошибок и восстановление данных.
- **Подготовить среду для реальных проектов**: интеграция с Jupyter Notebook, PyCharm, использование PySpark, Pandas, NumPy; применение Airflow для оркестрации.

## Доступные источники данных

В семинаре используются несколько типов источников, чтобы показать разные сценарии:

- **Симулятор на базе Raspberry Pi** — программная имитация датчиков, которая генерирует потоки данных, имитируя реальные IoT‑устройства.
- **CSV‑файлы с образцами данных** — загружаются и отправляются в Kafka каждые 5 секунд; служат для отладки пайплайна и проверки логики агрегации.
- **Jar‑файл как инструмент отправки данных** — универсальный источник: через аргументы (IP, порт, тема, интервал) можно направлять данные из разных источников в одну или несколько тем Kafka.
- **Необработанные данные с датчиков** — в сценарии они сначала попадают в платформу Hadoop (для хранения и «сырой» истории), а затем обрабатываются Spark.
- **Данные для агрегации и витрин** — после обработки в Spark данные записываются в PostgreSQL (в том числе в гипертаблицы для временных рядов) и далее используются для мониторинга в Grafana.

Такой набор источников позволяет показать полный цикл: от «грязных» данных и их хранения до очищенных витрин и дашбордов.

## Симулятор Raspberry Pi для обработки данных

Здесь важно сразу прояснить: в этом проекте **Raspberry Pi — это не физическое устройство**, а **программный симулятор**, который эмулирует поведение датчиков и отправку телеметрии.

Как он используется в пайплайне:

1. **Генерация потока данных.** Симулятор формирует сообщения, похожие на показания датчиков (температура, влажность и т. п.) и отправляет их в Kafka. Это позволяет тестировать пайплайн без реального «железа».
2. **Имитация реального сценария IoT.** Данные идут в потоковом режиме, с определённой частотой (например, каждые 5 секунд), что близко к реальным условиям работы с датчиками.
3. **Отправка через jar‑файл.** Симулятор интегрирован с утилитой на Java (jar‑файл), которая берёт данные (в том числе из CSV) и отправляет их в заданную тему Kafka, принимая параметры: IP‑адрес брокера, порт, название темы, интервал отправки.
4. **Масштабируемость.** Один и тот же jar‑файл можно использовать для нескольких источников данных, меняя только аргументы. Это удобно для тестирования разных сценариев нагрузки и проверки устойчивости пайплайна.
5. **Остановка и контроль.** Симулятор можно автоматически остановить, чтобы проверить, как ведёт себя пайплайн при пустом потоке (например, микропакеты становятся пустыми, Spark корректно завершает обработку).

**Зачем это нужно в обучении:**

- Позволяет участникам **сразу начать практиковаться** без закупки и настройки оборудования.
- Даёт возможность **воспроизводить сценарии ошибок** (потеря пакетов, повторная отправка, пустые пакеты) и отрабатывать восстановление с помощью контрольных точек.
- Демонстрирует **разделение ответственности**: симулятор отвечает за генерацию, Kafka — за буферизацию и доставку, Spark — за обработку, PostgreSQL — за хранение, Grafana — за визуализацию.

## Какой проект создаётся по ходу семинара

По ходу семинара участники собирают **сквозной потоковый пайплайн обработки телеметрии в реальном времени** — полноценный прототип инженерной системы уровня production-lite. Это не учебный пример «в одну строчку», а многокомпонентная архитектура, где каждый узел решает конкретную задачу и отрабатываются типичные производственные проблемы (отказоустойчивость, мониторинг, настройка ресурсов).

### Что именно делают шаг за шагом

- **Разворачивают трёхнодовый кластер в Docker**: настраивают память и ядра, задают параметры драйвера и исполнителей, уменьшают число разделов для производительности.
- **Создают темы в Kafka** и отправляют туда данные: через CSV-файлы и через Java-jar с аргументами (IP, порт, тема, интервал).
- **Читают поток из Kafka в Spark Streaming**, делают микропакетную обработку: парсинг, split/regex, приведение типов, преобразование временных меток.
- **Агрегируют данные по окнам** (2–4 секунды) и считают средние по температуре, влажности и т. п.
- **Пишут агрегированные данные в PostgreSQL**, в том числе в гипертаблицы (для временных рядов).
- **Добавляют контрольные точки (checkpoints)** для восстановления состояния при сбоях.
- **Подключают Grafana** к PostgreSQL и выводят дашборд с метриками: количество записей, длительность пакетов, скорость обработки.
- **Оркестрируют процесс через Airflow**: используют BashOperator и SDFS Sensor, запускают джобы по расписанию (cron), автоматизируют реакцию на поступление данных.
- **Отправляют «сырые» данные в Hadoop** для долгосрочного хранения и возможности повторной обработки.

## Предметная область проекта

Это **IoT‑телеметрия с датчиков** (имитация показаний устройств), по сути — **система мониторинга параметров среды в реальном времени**.

### Какие данные обрабатываются

- Температура, влажность и другие метрики с «датчиков».
- Идентификатор устройства/источника (название устройства).
- Временные метки (event time) для оконных агрегаций.
- Метаданные потока (интервал отправки, источник, тема Kafka).

Данные приходят в виде потока сообщений, каждое из которых соответствует одному измерению.

### Для чего такой пайплайн нужен на практике

Такой тип систем встречается в:

- **Промышленном IoT и SCADA**: мониторинг температуры и влажности в цехах, на складах, в ЦОДах.
- **Умных зданиях**: контроль микроклимата, энергопотребления, состояния оборудования.
- **Логистике и холодовой цепи**: отслеживание условий перевозки чувствительных грузов.
- **Сельском хозяйстве**: теплицы, фермы, метеостанции.

В рамках семинара это **универсальный шаблон**: он показывает, как из «грязного» потока событий сделать витрину данных и дашборд, сохранив при этом отказоустойчивость и возможность масштабирования.

## Откуда брать образы и что именно поднимать

Для этого семинара стек почти всегда такой:

- **Kafka + ZooKeeper** (или KRaft) — для очередей сообщений.
- **Spark** (отдельный контейнер/кластер) — для потоковой обработки.
- **PostgreSQL** — для витрин и агрегаций.
- **Grafana + Prometheus** (опционально) — для мониторинга.
- **Airflow** (опционально) — для оркестрации.

Готовые образы — это официальные образы на Docker Hub: `bitnami/kafka`, `apache/spark`, `postgres`, `grafana/grafana` и т. п. Тебе не нужно ничего собирать вручную.

### Минимальный docker-compose.yml для старта

Вот базовый вариант, который даёт тебе «тот самый» старт в терминале:

```yaml
version: "3.8"

services:
  zookeeper:
    image: bitnami/zookeeper:3.8
    environment:
      - ALLOW_ANONYMOUS_LOGIN=yes
    ports:
      - "2181:2181"

  kafka:
    image: bitnami/kafka:3.7
    depends_on:
      - zookeeper
    environment:
      - KAFKA_CFG_ZOOKEEPER_CONNECT=zookeeper:2181
      - KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://kafka:9092
      - KAFKA_CFG_LISTENERS=PLAINTEXT://0.0.0.0:9092
      - ALLOW_PLAINTEXT_LISTENER=yes
      - KAFKA_AUTO_CREATE_TOPICS_ENABLE=true
    ports:
      - "9092:9092"

  spark-master:
    image: apache/spark:3.5.0
    command: /opt/spark/bin/start-master.sh && tail -f /opt/spark/logs/*.log
    environment:
      - SPARK_MASTER_HOST=spark-master
    ports:
      - "8080:8080"

  spark-worker:
    image: apache/spark:3.5.0
    depends_on:
      - spark-master
    command: /opt/spark/bin/start-worker.sh spark://spark-master:7077
    deploy:
      replicas: 2

  postgres:
    image: postgres:15
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
      POSTGRES_DB: iot_telemetry
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
    depends_on:
      - postgres

volumes:
  pgdata:
```

Запускаешь одной командой:

```bash
docker compose up -d
```

И дальше ты в том же положении, что и на семинаре: Kafka слушает на `localhost:9092`, Spark-master на порту `8080`, PostgreSQL на `5432`.

## Как начать работать «вместе с преподавателем»

На практике синхронность достигается не готовыми образами, а **одинаковыми инструкциями**. Вот как подстроиться:

1. **Следуй тем же шагам из терминала.** Преподаватель делает: `docker compose up`, ты делаешь то же самое. Он создаёт тему — ты создаёшь ту же тему.
2. **Используй те же CLI‑утилиты внутри контейнеров.** Например, создание темы Kafka:
   ```bash
   docker exec -it <kafka-container> kafka-topics.sh \
     --bootstrap-server kafka:9092 \
     --create --topic sensor_data --partitions 3 --replication-factor 1
   ```
   (Имя контейнера узнаётся через `docker ps`.)
3. **Держи одинаковые имена тем, БД, таблиц.** Если преподаватель говорит «тема `sensor_data`», ты тоже используешь `sensor_data`. Это критично: если названия не совпадут, пайплайн не сойдётся.
4. **Используй одни и те же тестовые данные.** Часто на семинарах дают CSV‑файл с телеметрией. Скачай его и положи в общую папку, которую пробросишь в контейнер через `volumes` в compose.
5. **Синхронизируй версии.** Если преподаватель использует Spark 3.5, Kafka 3.7 — ставь такие же. Версии сильно влияют на команды и поведение.

## Что делать вместо «готового образа» с симулятором Raspberry Pi

Симулятор — это просто скрипт, который шлёт данные в Kafka. У тебя есть три пути, чтобы не зависеть от чужого образа:

1. **Python‑продюсер** (самый простой вариант):
   ```python
   from kafka import KafkaProducer
   import json, time, random

   producer = KafkaProducer(
       bootstrap_servers="localhost:9092",
       value_serializer=lambda v: json.dumps(v).encode("utf-8")
   )

   while True:
       msg = {
           "device_id": "sensor_01",
           "temperature": round(random.uniform(20, 30), 2),
           "humidity": round(random.uniform(40, 60), 2),
           "ts": int(time.time())
       }
       producer.send("sensor_data", value=msg)
       time.sleep(5)
   ```
   Запускай этот скрипт локально или в отдельном контейнере — эффект тот же, что и у «симулятора».

2. **Java .jar‑файл** (как в семинаре). Если преподаватель даёт jar — скачиваешь и запускаешь:
   ```bash
   java -jar simulator.jar --broker localhost:9092 --topic sensor_data --interval 5
   ```
3. **Console producer** для быстрой проверки:
   ```bash
   docker exec -it <kafka-container> kafka-console-producer.sh \
     --broker-list kafka:9092 --topic sensor_data
   ```
   Потом вручную вставляешь JSON‑сообщения.

## Частые проблемы и как их обойти

- **«Не могу подключиться к Kafka из Spark»**: проблема почти всегда в `advertised.listeners`. В compose выше я уже настроил `PLAINTEXT://kafka:9092` — это позволяет другим контейнерам (Spark) подключаться по имени сервиса.
- **«Данные не приходят»**: проверь, что имя темы точно совпадает и что consumer запущен с `--from-beginning`, если данные отправлены до старта consumer’а.
- **«Spark не видит тему»**: убедись, что зависимости в `spark-submit` включают коннектор Kafka (обычно `spark-sql-kafka-0-10` нужной версии).

## 1. Про предупреждение `version is obsolete`

Это не ошибка, а просто предупреждение: в современных Docker Compose атрибут `version` больше не нужен, движок сам понимает формат.

**Что сделать:** просто удали строку `version: "3.8"` из `docker-compose.yaml`. Файл станет чище, и предупреждение исчезнет.

---

## 2. Про ошибку подключения к Docker API

Сообщение `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine` говорит о том, что CLI пытается подключиться к «Linux Engine», которого у тебя сейчас нет. Это частая ситуация на Windows, когда:

- Docker Desktop не запущен,
- или в настройках выбран не тот движок,
- или CLI «запомнил» неверный контекст.

### Шаги, чтобы всё починить

1. **Проверь, запущен ли Docker Desktop.** На Windows иконка в трее должна быть зелёной и показывать статус «Running». Если нет — запусти приложение и дождись полной загрузки (иногда это занимает минуту).
2. **Посмотри, какой движок выбран.** В Docker Desktop зайди в Settings → General и убедись, что включён WSL 2 или Desktop VM (не старый «Hyper-V only», если он у тебя не настроен).
3. **Проверь контекст Docker.** Выполни в терминале:
   ```bash
   docker context ls
   ```
   Если там есть контексты кроме `default`, переключись на дефолтный:
   ```bash
   docker context use default
   ```
4. **Попробуй простую команду.** После этого проверь, что всё работает:
   ```bash
   docker ps
   ```
   Должно показать пустой список (если нет запущенных контейнеров) без ошибок.
5. **Запускай compose уже после этого:**
   ```bash
   docker compose up -d
   ```
   (именно `docker compose`, без дефиса — это современный плагин).
